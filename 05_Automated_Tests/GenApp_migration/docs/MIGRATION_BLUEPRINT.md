# GenApp (DB2 + VSAM) → PostgreSQL Migration Blueprint

**Source system:** IBM GenApp — a CICS/COBOL insurance application with two
alternate persistence backends: DB2 for z/OS (tables: `customer`,
`customer_secure`, `policy`, `endowment`, `house`, `motor`, `commercial`,
`claim`) and VSAM KSDS (`KSDSCUST`, `KSDSPOLY`). This document reflects the
*actual* schema and copybooks found in `source.zip`, not a generic template —
every field below was verified against `ddl/db2_source_schema.sql` (extracted
from `reference/jcl/db2cre.jcl`) and the copybooks in `copybooks/`.

**Target:** PostgreSQL, schema `genapp` (see `sql/02_target_schema.sql`).

## 1. Data Type Mapping Table

### 1.1 DB2 for z/OS → PostgreSQL

| DB2 Type | Example (from db2cre.jcl) | PostgreSQL Type | Notes |
|---|---|---|---|
| `CHAR(n)` | `firstName CHAR(10)` | `VARCHAR(n)` | PostgreSQL's `CHAR(n)` space-pads on read, which surprises app code expecting DB2's non-padded comparison semantics in most drivers. `VARCHAR(n)` keeps the same length **validation** without the padding gotcha. Use `CHAR(n)` only if a downstream consumer genuinely depends on fixed-width padded output. |
| `VARCHAR(n)` | `endowment.paddingData VARCHAR(32606)` | `VARCHAR(n)` or `TEXT` | PostgreSQL has no meaningful performance difference between `VARCHAR(n)` and `TEXT`; prefer `TEXT` for very large or genuinely unbounded fields (no practical reason to keep the 32606 cap). |
| `INTEGER` | `customerNumber`, `policyNumber` | `INTEGER` | Direct mapping, same range (-2³¹..2³¹-1). |
| `SMALLINT` | `bedrooms`, `commission`, `firePeril` | `SMALLINT` | Direct mapping. |
| `INTEGER GENERATED BY DEFAULT AS IDENTITY (START WITH n, INCREMENT BY n, CACHE n)` | `customerNumber`, `policyNumber`, `claimNumber` | `INTEGER GENERATED BY DEFAULT AS IDENTITY (START WITH n INCREMENT BY n)` | Nearly 1:1 portable syntax (PostgreSQL 10+). `CACHE` is supported too if sequence-cache behavior matters; omitted here since it's a performance tuning detail, not a correctness one. |
| `DATE` | `dateOfBirth`, `issueDate`, `claimDate` | `DATE` | Direct mapping. DB2 stores as an internal packed form; PostgreSQL stores as a 4-byte integer day-offset — both compare/sort correctly, no conversion logic needed beyond format (`YYYY-MM-DD` on both sides). |
| `TIMESTAMP` | `policy.lastChanged`, `commercial.requestDate` | `TIMESTAMP` | Direct mapping. `... NOT NULL WITH DEFAULT` (DB2's "default to current timestamp") → `NOT NULL DEFAULT now()` in PostgreSQL. |
| `CLOB(n)` *(not present in this schema, but common in DB2 shops)* | — | `TEXT` | PostgreSQL `TEXT` has no declared size limit and uses TOAST for out-of-line storage automatically — no CLOB-style "locator" plumbing needed in application code. |
| `BLOB(n)` *(not present in this schema, but common in DB2 shops)* | — | `BYTEA` | Same rationale as CLOB→TEXT; `BYTEA` handles arbitrary binary size via TOAST. |
| `CCSID EBCDIC` table/column attribute | every table in this schema | *(n/a — encoding is a client/database-wide setting)* | PostgreSQL databases have one `SERVER_ENCODING` (use `UTF8`); there is no per-column EBCDIC/ASCII attribute. All EBCDIC-encoded DB2 export data must be transcoded to UTF-8 **during** the ETL step (see Section 4), not represented as a column property. |

### 1.2 COBOL Copybook Clauses (VSAM) → PostgreSQL

These map COBOL storage clauses — used in both the DB2 host-variable
copybooks (`copybooks/lgpolicy.cpy`) and the true VSAM physical record
layouts we reverse-engineered from the CICS `WRITE FILE` calls
(`copybooks/derived_vsam_customer.cpy`, `copybooks/derived_vsam_policy.cpy`)
— to native PostgreSQL types.

| COBOL Clause | Example (from this codebase) | PostgreSQL Type | Notes |
|---|---|---|---|
| `PIC X(n)` | `CUST-EMAIL-ADDRESS PIC X(100)` | `VARCHAR(n)` | Alphanumeric, space-padded in the source; the loader right-trims trailing spaces on decode (see `ebcdic_utils.decode_ebcdic_text`). |
| `PIC 9(n)` (unsigned DISPLAY) | `CUST-NUM PIC 9(10)` | `INTEGER` / `BIGINT` (or `NUMERIC(n)` if `n > 18`) | Zoned-decimal, one byte per digit. Choose `INTEGER` for n≤9, `BIGINT` for n≤18. |
| `PIC S9(n)` (signed DISPLAY) | *(not present in this schema's VSAM records, but common elsewhere)* | `INTEGER`/`BIGINT`/`NUMERIC` | Same as above; the **sign lives in the zone nibble of the last byte** (EBCDIC overpunch: `{`=+0…`I`=+9, `}`=-0…`R`=-9), not as a separate character — see `ebcdic_utils.unpack_zoned_display`. |
| `PIC S9(n)V9(m) COMP-3` | *(not present in this schema, but the toolkit fully supports it — see below)* | `NUMERIC(n+m, m)` | Packed decimal: 2 BCD digits per byte + 1 sign nibble, formula `bytes = floor((n+m)/2) + 1`. Must be binary-unpacked, never text-decoded — see Section 4. |
| `PIC 9(n) COMP` / `COMP-4` | `WS-CUSTOMER-LEN PIC S9(4) COMP` | `SMALLINT`/`INTEGER`/`BIGINT` | Big-endian binary integer. Storage length is **not** proportional to digit count in a simple way — it follows IBM Enterprise COBOL's halfword/fullword/doubleword rule: 1-4 digits→2 bytes, 5-9 digits→4 bytes, 10-18 digits→8 bytes. |
| `OCCURS n TIMES` | `polloo2.cpy`: `CA-POLICIES OCCURS 5 TIMES` | Child table with FK + `occurs_index` column | See Section 2. |
| `OCCURS n TIMES DEPENDING ON x` | *(not present in this schema, supported by the toolkit)* | Same child-table pattern; only `x` rows are populated per parent | The `DEPENDING ON` counter becomes informational only — PostgreSQL doesn't need a stored "how many rows are valid" counter once the rows are properly normalized. |
| `REDEFINES` | `POLICY-RECORD` in `derived_vsam_policy.cpy`: one 43-byte area reinterpreted 4 ways by policy type | Either (a) nullable variant columns on one table, or (b) dispatch to separate per-variant tables | **This schema uses pattern (b)**, because the four REDEFINES variants here correspond to genuinely distinct DB2 tables (`endowment`/`house`/`motor`/`commercial`) that already exist as the migration target — see Section 2 for why this is preferable to pattern (a) when a natural relational target already exists. |
| `88`-level condition names (`VALUE` clauses) | *(none in this schema)* | `CHECK` constraint or lookup table | Not physical storage — carries no bytes of its own, so it's dropped from byte-offset math but should become a `CHECK (col IN (...))` constraint or reference table if the business rule matters. |

## 2. Handling VSAM Hierarchies: OCCURS and REDEFINES

### 2.1 The concrete case in this codebase: `KSDSPOLY`'s REDEFINES-by-type

`copybooks/derived_vsam_policy.cpy` (reverse-engineered from the `WF-Policy-Info`
working-storage record in `reference/cobol/lgapvs01.cbl`) is a textbook
"discriminated union" VSAM record:

```cobol
01  POLICY-RECORD.
    05  POLICY-REQUEST-ID     PIC X(01).   *> discriminator: C/E/H/M
    05  POLICY-CUSTOMER-NUM   PIC X(10).
    05  POLICY-NUM            PIC X(10).
    05  POLICY-DATA           PIC X(43).   *> 43 raw bytes, reinterpreted 4 ways
    05  POLICY-C-DATA REDEFINES POLICY-DATA.  *> Commercial fields
    05  POLICY-E-DATA REDEFINES POLICY-DATA.  *> Endowment fields
    05  POLICY-H-DATA REDEFINES POLICY-DATA.  *> House fields
    05  POLICY-M-DATA REDEFINES POLICY-DATA.  *> Motor fields
```

The same 43 bytes mean something different depending on the value of the
1-byte discriminator field. This is the single hardest pattern to migrate
correctly, and getting it wrong silently corrupts data (e.g. reading
`POLICY-M-VALUE` out of a record that is actually type `H` returns garbage
that happens to parse as a number).

**Step-by-step strategy used by `scripts/load_vsam_policy.py`:**

1. **Never decode blind.** Always read the discriminator field first
   (`POLICY-REQUEST-ID`), before touching any REDEFINES variant.
2. **Branch on the discriminator to choose exactly one variant's field
   list.** The parser (`copybook_parser.py`) computes byte offsets for
   *all four* variants (they all legitimately start at byte 21, since
   REDEFINES fields share their target's offset — verified by
   `_compute_offsets()`), but the loader only decodes the one variant
   that matches the discriminator value it already read.
3. **Route each variant to its own relational home**, not to nullable
   columns bolted onto one wide table. Because a natural target already
   existed here (DB2's `endowment`/`house`/`motor`/`commercial` tables),
   the loader inserts the common fields into `genapp.policy` and the
   type-specific fields into the matching detail table, joined 1:1 on
   `policy_number`. This is strictly better than a single wide table
   with 20+ mostly-NULL columns: every column in every table is always
   meaningful, foreign keys enforce that a policy has *exactly one*
   detail row of the correct type (via the app/ETL layer, since SQL
   can't natively express "exactly one of these 4 tables"), and query
   plans don't waste I/O scanning irrelevant NULL columns.
4. **Document, don't silently drop, the fields VSAM doesn't carry.**
   `KSDSPOLY` is a *summary* record — it lacks `issueDate`, `expiryDate`,
   `brokerId`, `payment`, `commission`, and most type-specific detail
   fields that exist in DB2's fuller row layout. The loader leaves those
   columns `NULL` rather than guessing, and the script's docstring calls
   this out explicitly so a migration engineer doesn't mistake NULL for
   "successfully migrated as zero/empty."

### 2.2 General pattern: OCCURS → child table

Although this specific schema's only `OCCURS` clause
(`polloo2.cpy`: `CA-POLICIES OCCURS 5 TIMES`) lives in a CICS commarea
(request/response scratch memory, not a persisted VSAM record — so nothing
to migrate there), the toolkit's copybook parser and byte-offset engine
(`copybook_parser.py`) fully support `OCCURS` and `OCCURS ... DEPENDING ON`
for any copybook you point it at, using this normalization pattern:

1. Compute the per-occurrence length and stride (`Field.length`,
   `Field.occurs_max`).
2. Create a child table: `{parent_table}_{occurs_group_name}` with a
   `BIGSERIAL` surrogate key, a foreign key back to the parent's primary
   key, and an `occurs_index SMALLINT` column recording which occurrence
   (0-based) each row came from.
3. Add a `UNIQUE (parent_id, occurs_index)` constraint so re-running the
   loader is idempotent (`ON CONFLICT DO NOTHING`/`DO UPDATE`).
4. For `OCCURS ... DEPENDING ON counter-field`, only emit rows for
   `0..counter_field-1` — the counter itself does not need to be stored
   as a column in PostgreSQL, since `COUNT(*) ... WHERE parent_id = ...`
   on the child table always gives the correct live count.

### 2.3 Decision guide: nullable columns vs. child/variant tables

| Situation | Recommended pattern |
|---|---|
| REDEFINES variants correspond to genuinely different business entities that already have (or should have) their own tables | Dispatch to separate tables (Section 2.1's approach) |
| REDEFINES is a minor reinterpretation of a small number of fields, with no natural separate entity | Nullable variant columns on the same table, prefixed by variant name (e.g. `passport_number`, `license_number`) |
| OCCURS represents a genuinely repeating sub-entity (line items, contacts, retry attempts) | Child table (1st normal form) |
| OCCURS is small (2-3) and semantically fixed-position (e.g. "primary phone" / "secondary phone", never iterated over) | Flatten to numbered columns (`phone_1`, `phone_2`) instead of a child table — a child table adds a join for no normalization benefit when the position itself is the meaning |

## 3. Schema Conversion Best Practices

Applied throughout `sql/02_target_schema.sql`, converting
`ddl/db2_source_schema.sql`:

- **Naming convention**: DB2 columns were mixed-case unquoted
  (`customerNumber`, `firstName`) — DB2 folds unquoted identifiers to
  uppercase internally but most tooling displays/accepts them
  case-insensitively. PostgreSQL folds unquoted identifiers to
  **lowercase**, and mixed-case unquoted names become a constant
  footgun (`SELECT customerNumber` silently becomes
  `SELECT customernumber`, while application code sending exact-case
  identifiers with quotes would break). We standardized on
  `snake_case` throughout (`customer_number`, `first_name`) rather than
  fighting PostgreSQL's folding rules with quoted mixed-case identifiers.
- **Primary keys**: DB2's `GENERATED BY DEFAULT AS IDENTITY (START WITH
  n, INCREMENT BY n, CACHE n)` ports almost verbatim to PostgreSQL 10+'s
  identity columns. `GENERATED BY DEFAULT` (rather than `ALWAYS`) was
  preserved because both the VSAM loader and the DB2 CSV loader need to
  **insert explicit key values** carried over from the legacy system
  (`OVERRIDING SYSTEM VALUE` — see `load_vsam_customer.py` and
  `load_vsam_policy.py`), not generate fresh ones.
- **Foreign keys & cascade rules**: every `ON DELETE CASCADE` in the DB2
  DDL (customer→policy, policy→endowment/house/motor/commercial/claim)
  was preserved as-is; PostgreSQL's `FOREIGN KEY ... ON DELETE CASCADE`
  syntax is identical to DB2's.
- **Indexes**: DB2's `CREATE UNIQUE INDEX ... CLUSTER` (a clustering
  index, which DB2 uses to physically order table rows) has no direct
  PostgreSQL equivalent as an ongoing property — PostgreSQL's `CLUSTER
  table USING index` is a one-time physical reorganization command, not
  a maintained property, so tables drift back out of cluster order as
  they're updated. We created the equivalent `UNIQUE INDEX` for
  correctness (`iCustomer`, `iPolicy`, etc.) and omitted a one-time
  `CLUSTER` command from the DDL itself — run it manually post-load if
  physical ordering matters for a specific reporting workload:
  `CLUSTER genapp.policy USING ix_policy_customer_number;`
- **Storage groups, tablespaces, buffer pools, CCSID**: all z/OS
  storage-management clauses (`STOGROUP`, `IN <db>.<tablespace>`,
  `BUFFERPOOL BP1`, `CCSID EBCDIC`) were dropped from the target DDL —
  they configure *how* DB2 physically stores data on z/OS disk, which
  has no PostgreSQL analog. PostgreSQL's closest concept
  (`TABLESPACE`) maps storage to a filesystem path, not a buffer-pool
  policy, and is only worth adding if you have a specific I/O isolation
  requirement (e.g. putting `claim`'s large `TEXT` columns on faster
  storage).
- **JCL symbolic substitution variables** (`<DB2DBID>`, `<SQLID>`, etc.)
  were resolved away entirely — they're a z/OS job-submission mechanism
  with no meaning outside that context.

## 4. Data Unpacking Strategy: EBCDIC and COMP-3

This is implemented in `scripts/ebcdic_utils.py` and exercised end-to-end
by `scripts/load_vsam_customer.py` / `scripts/load_vsam_policy.py`.

### 4.1 EBCDIC → UTF-8

- **Real mainframe extracts** (produced via `IDCAMS REPRO` from the VSAM
  cluster to a sequential dataset, then transferred **in BINARY mode**
  — never ASCII/text FTP mode, which would corrupt binary numeric
  fields) are EBCDIC-encoded end to end. Decode with Python's built-in
  `cp037` codec (US/Canada EBCDIC) — or `cp500` (International EBCDIC)
  or `cp1140` (Euro-enabled variant of cp037) depending on the source
  shop's code page. This toolkit defaults to `cp037` and exposes an
  `--encoding` flag on both VSAM loaders for shops using a different
  code page.
- **Trailing-space trimming**: COBOL space-pads `PIC X` fields to their
  declared length; `decode_ebcdic_text()` right-trims on decode so
  PostgreSQL `VARCHAR` columns don't carry meaningless trailing
  whitespace.
- **This codebase's actual sample data is a special case**: the files
  in `reference/data/` (`ksdscust.txt`, `ksdspoly.txt`) are **plain
  ASCII text**, not raw EBCDIC binary — a convenience transcoding done
  for this analysis workspace, confirmed via `file reference/data/*.txt`
  → `ASCII text`. Both loaders default their `--encoding` flag
  appropriately (`cp037` for `run_migration.py`'s general-purpose
  default, `ascii` when pointed at `sample_data/` specifically) — **do
  not assume every "flat file from the mainframe team" is EBCDIC binary
  without checking; ask, or run `file` on it first.**

### 4.2 COMP-3 (packed decimal) unpacking

Although this specific GenApp schema's VSAM records use only unsigned
zoned-decimal (`PIC 9(n)` DISPLAY) numerics — no `COMP-3` fields appear
in `derived_vsam_customer.cpy` or `derived_vsam_policy.cpy` — this is a
**very** common clause in other IBM shops' copybooks (it appears
throughout the DB2 host-variable copybook `copybooks/lgpolicy.cpy`'s
`WS-*-LEN` fields, for instance, as `COMP` rather than `COMP-3`), so the
toolkit implements full COMP-3 support for reuse against other
copybooks in this estate:

1. Each byte holds **two BCD (binary-coded decimal) digits**, except the
   last byte, whose low nibble is the **sign**, not a digit:
   `0xC`/`0xF` = positive, `0xD` = negative, `0xB` = unsigned-negative
   (rare).
2. Storage length formula: `bytes = floor(total_digits / 2) + 1`.
3. Unpacking is **pure binary bit-shifting** (`(byte >> 4) & 0x0F` for
   the high nibble, `byte & 0x0F` for the low nibble) — it is **not**
   a text/character decode operation, so no EBCDIC codec applies to
   COMP-3 fields at all. See `ebcdic_utils.unpack_comp3()`.
4. Apply the implied decimal point from the `V` in the PIC clause
   *after* unpacking the full integer value (e.g. `S9(9)V99 COMP-3` →
   unpack as an 11-digit integer, then divide by 100).

### 4.3 COMP / COMP-4 (binary integer) unpacking

- Big-endian (`>h`/`>i`/`>q` in Python's `struct` module) binary
  integers. Storage length is **not** simply "digits ÷ something" — it
  follows IBM's fixed halfword(2)/fullword(4)/doubleword(8) size
  bands based on declared digit count (1-4→2 bytes, 5-9→4 bytes,
  10-18→8 bytes), implemented in `copybook_parser._comp_length()`.
- `WS-CUSTOMER-LEN PIC S9(4) COMP` in `copybooks/lgpolicy.cpy` is a
  real example from this codebase (a 2-byte signed halfword).

### 4.4 Recommended extraction pipeline for real (non-sample) data

```
Mainframe VSAM (KSDSCUST/KSDSPOLY)
   │  IDCAMS REPRO INFILE(KSDSCUST) OUTFILE(SEQOUT)
   ▼
Sequential dataset (RECFM=FB, LRECL=225 or 64)
   │  FTP BINARY (never ASCII mode) — or DFSMS/DFDSS to a zFS file,
   │  or Db2 Connect/zLinux Unix System Services `cp` if co-located
   ▼
Flat file on this migration host, still EBCDIC-encoded
   │  scripts/load_vsam_customer.py --encoding cp037
   │  scripts/load_vsam_policy.py   --encoding cp037
   ▼
PostgreSQL genapp.customer / genapp.policy + detail tables
```

For the DB2 side, use DB2's own `EXPORT`/`UNLOAD` utility with a
delimited (`DEL`) output format — this already renders EBCDIC-internal
values as readable text in the export file's chosen code page, so
`scripts/db2_loader.py` only needs standard CSV parsing plus a bulk
`COPY`, not byte-level unpacking.

## 5. Tooling Recommendations

| Category | Tool | Why it fits this migration |
|---|---|---|
| **This custom toolkit** (`scripts/`) | Python + `psycopg2` | Purpose-built for the exact REDEFINES-by-type and byte-offset patterns in `KSDSPOLY`/`KSDSCUST`; free, fully inspectable, easy to extend to more copybooks in this estate (JCL shows ~20 more COBOL programs with their own working-storage records, e.g. `lgacdb02.cbl`, `lgtestp*.cbl`). |
| **Open-source: AWS SCT (Schema Conversion Tool) + DMS** | AWS | Free. SCT can auto-convert DB2 z/OS DDL to PostgreSQL DDL (handles most of Section 3 mechanically) and flags manual-review items. DMS handles ongoing CDC replication from DB2 during a phased cutover, which is valuable if GenApp needs to stay live during migration. Does **not** understand VSAM/COBOL copybooks — VSAM still needs a tool like this one or a commercial mainframe-aware ETL product. |
| **Open-source: pgloader** | Free | Excellent for bulk-loading DB2 CSV/UNL exports into PostgreSQL with type coercion rules defined in a small DSL; faster to stand up than hand-written Python for the DB2-only tables if no COBOL-copybook-driven unpacking is needed. |
| **Open-source: Apache NiFi** | Free | If the migration needs to become a *repeatable, monitored, scheduled* pipeline (not a one-time cutover), NiFi's flow-based processors can wrap this toolkit's Python scripts as `ExecuteStreamCommand` steps and add retry/alerting/lineage tracking for free. |
| **Commercial: IBM Data Contract/Compose, or IBM's own z/OS Connect + Db2 Migration tooling** | IBM | Since this *is* an IBM sample estate, IBM's own migration tooling (Db2 Data Gate, Data Virtualization Manager) has first-party support for the exact DDL dialect in `db2cre.jcl` and can automate the STOGROUP/TABLESPACE stripping in Section 3. Worth evaluating if the shop already has an IBM support contract. |
| **Commercial: Precisely Connect (formerly Syncsort/DMX-h)** | Precisely | Purpose-built mainframe-to-cloud ETL with native COBOL copybook import (drag-and-drop the exact `.cpy` files in `copybooks/`), including REDEFINES/OCCURS handling out of the box — reduces the custom-code surface this toolkit currently owns, at commercial license cost. Strong fit if this migration is the first of several mainframe estates to migrate (amortizes tool cost across projects). |
| **Commercial: BMC AMI Cloud / Compuware (BMC) Topaz** | BMC | Mainframe-native discovery and dependency analysis (useful for finding *every* COBOL program that touches `KSDSCUST`/`KSDSPOLY`/DB2 tables before cutover, not just the ones in this zip) — complements rather than replaces an ETL tool. |
| **Validation: Datold / custom row-count + checksum scripts** | Either | Regardless of ETL tool choice, always validate post-migration with row counts per table (`SELECT count(*)`) **and** a sampled field-level diff against the source (this exercise already caught one real data-quality issue — the malformed `bedrooms` field in `ksdspoly.txt` row 6 — by simply loading and eyeballing the result; see README "Known Data-Quality Findings"). |

**Recommendation for this specific estate**: given its small size (2 VSAM
files, 8 DB2 tables, ~30 COBOL programs) and that a working, tested toolkit
already exists in this repo, the marginal cost of adopting a commercial ETL
platform is unlikely to pay for itself unless (a) this is the first of many
mainframe estates the organization plans to migrate, or (b) the cutover
needs zero-downtime CDC replication (in which case AWS DMS or Precisely
Connect are the strongest free/commercial options respectively).
